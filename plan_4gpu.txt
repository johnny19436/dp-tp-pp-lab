# 4-GPU Single-Node Parallelism Experiment Plan
# File: plan_4gpu.txt

## Context

You are taking over an existing single-node distributed-training lab repository that was originally built and validated on:

- 2 × NVIDIA A100-SXM4-40GB
- NVLink / NV12 between the two GPUs
- Megatron-LM / Megatron Core
- BF16
- mock data
- GPT-style training
- NCCL microbenchmarks
- Nsight Systems profiling
- CSV result generation
- PDF report generation

IMPORTANT:

You are a NEW agent. You should assume the existing codebase was written for the previous 2-GPU experiment.

Do NOT blindly overwrite or replace the old experiment.

Instead:

1. Inspect the existing repository carefully.
2. Understand how the previous 2-GPU scripts, result parsers, Nsight profiling, CSV generation, and report generation work.
3. Reuse or generalize the existing code where appropriate.
4. Create NEW 4-GPU experiment scripts/configurations/results while preserving the old 2-GPU experiment artifacts.
5. Treat the old 2-GPU codebase as a reference implementation, not as something that is already correct for 4 GPUs.
6. Explicitly validate all assumptions that change with world_size=4.

The previous experiment already established the following measured behavior:

- 1GPU throughput ≈ 16,172 tokens/s
- DP2 throughput ≈ 31,666 tokens/s
- DP2 strong-scaling efficiency ≈ 97.9%
- DP2 weak-scaling efficiency ≈ 99.3%
- TP2 throughput ≈ 19,620 tokens/s
- TP2 peak allocated memory ≈ 17.5 GB
- TP2 had heavy collective overhead in Nsight
- PP2 could trade memory for throughput by changing microbatch size
- The previous main model was approximately a 1.3B-class GPT-like model:
  - num_layers = 24
  - hidden_size = 2048
  - ffn_hidden_size = 8192
  - num_attention_heads = 16
  - seq_length = 2048
  - BF16
  - global_batch_size = 64
  - default micro_batch_size = 1
  - mock data

The purpose of this new experiment is NOT merely to rerun the same 2-GPU study with four GPUs.

The new experiment should answer two new questions:

A. How does the original model scale from 1 → 2 → 4 GPUs under pure Data Parallelism?

B. What happens when the model is made large enough that a single 40 GB A100 can no longer train it, so that model parallelism becomes necessary?

This is still SINGLE NODE ONLY.

Do NOT work on:

- RDMA
- InfiniBand
- RoCE
- multi-node
- FSDP
- ZeRO
- expert parallelism
- context parallelism
- FP8
- offloading
- heterogeneous GPUs

unless specifically required to fix a correctness issue. If such a change is required, document it and ask before making it part of the main benchmark.

6. CREATE A LARGER MODEL FOR CAPACITY EXPERIMENTS
--------------------------------------------------

Now introduce a NEW larger GPT-like model.

Target starting point:

num_layers = 20
hidden_size = 3072
ffn_hidden_size = 12288
num_attention_heads = 24
seq_length = 2048
vocab_size ≈ 32000
precision = BF16
micro_batch_size = 1

This should be around the low-2B parameter range.

The exact parameter count must be calculated and reported.

The design goal is:

- 1GPU should OOM during training, or be clearly beyond a safe memory margin
- TP2 should fit
- PP2 should fit
- TP2×DP2 should fit on 4 GPUs
- PP2×DP2 should fit on 4 GPUs

Do NOT arbitrarily shrink the model just to make 1GPU pass.

The point is specifically to create a model where model parallelism is required.

However:

If the proposed model unexpectedly fits on 1 GPU with comfortable memory headroom, increase model size carefully.

If TP2 or PP2 unexpectedly OOMs, reduce model size minimally.

Any adjustment must be:

- documented
- applied consistently
- frozen before comparing configurations

Once a working large-model configuration is selected, freeze it for all main large-model runs.

15. FAIRNESS RULES
--------------------------------------------------

Main comparisons must be apples-to-apples.

For each directly compared set, keep constant:

- model architecture
- sequence length
- precision
- optimizer
- mock-data setup
- global batch for strong-scaling comparison
- warmup policy
- measured-iteration policy

Important:

Do not use a tuned PP run with micro_batch_size=4 as if it were directly equivalent to an untuned DP or TP run at micro_batch_size=1.

Separate:

MAIN FAIR COMPARISON:
micro_batch_size fixed

from:

TUNING / SENSITIVITY EXPERIMENTS:
PP microbatch sweep
optional sequence parallel
other tuning

The previous 2-GPU report showed that PP throughput could improve significantly when microbatch size increased because larger GEMMs became more efficient.

Do not misinterpret such a result as pure parallel-scaling gain.
